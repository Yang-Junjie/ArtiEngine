# docs/tasks

一个任务一份文件，命名 `YYYY-MM-DD-<kebab-slug>.md`。

这里的文件是**给执行者看的**，包括我、你、以及任何接手的 AI。所以每一份都必须自带足够的上下文：
读完这一份就能开工，不需要先去读整个仓库、也不需要问上一个人「你做到哪了」。

## 每份任务文件的固定结构

| 段 | 作用 |
| --- | --- |
| 头部元信息 | 状态、创建 / 更新日期、涉及哪几个仓库 |
| **交接区** | 全文唯一的可变段落：当前进度、下一步、决定记录、踩到的坑。**每次收工前必须更新** |
| 背景与现状 | 为什么做这件事，以及现状的**已验证证据**（命令 + 输出，不写「大概」） |
| 设计决定 | 每条都标「已定 / 待定」，已定的要写理由 —— 防止接手的人把它「简化」回去 |
| 任务清单 | 分阶段，每步带`文件 / 做法 / 验收`三行 |
| 端到端验收 | 全部做完之后怎么证明它真的成了 |
| 风险与注意 | 这个仓库特有的坑（submodule 三层、别跑 clang-format 之类） |

## 勾选约定

- `- [ ]` 未开始
- `- [x]` 已完成**且验收通过**（验收没过不许打勾）
- `- [~]` 进行中 —— 必须在同一行末尾追加 `← 进行中：<还差什么>`

## 接手流程

1. 读**交接区**，确认「下一步」和上一个人留下的决定 / 坑。
2. 从第一个没打勾的步骤开始，照它的`验收`那行做完再打勾。
3. 收工前回写交接区：进度、下一步、新增的决定和坑。
4. 任务全部完成后，把头部状态改成 `已完成`，并在交接区留一行结论。
